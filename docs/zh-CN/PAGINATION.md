# Crater 列表分页规范

本文规定 Crater 数据库主列表的分页协议、前后端职责和兼容边界。新增或改造列表时，应优先复用本文约定，不在业务页面中重新实现一套远程状态管理。

## 1. 适用范围

本规范适用于满足以下条件的列表：

- 数据来自 Crater 数据库；
- 数据量会随用户、作业或运行时间持续增长；
- 页面需要搜索、筛选、排序或翻页；
- 前端不需要一次拿到全部数据才能完成业务操作。

以下数据不直接套用该协议：

- Kubernetes 节点、Pod 等一次性资源快照；
- storage-server 返回的文件目录；
- 下拉框、表单候选项等需要完整集合的选择数据；
- 固定数量的系统配置和摘要数据。

这些场景如果出现规模问题，应分别设计快照分页、游标分页或异步搜索选择器，不能在前端伪装成数据库分页。

## 2. HTTP 协议

### 2.1 请求参数

公共参数如下：

| 参数        | 类型    | 默认值       | 说明                               |
| ----------- | ------- | ------------ | ---------------------------------- |
| `page`      | integer | `1`          | 从 1 开始的页码                    |
| `page_size` | integer | `10`         | 每页条数，当前统一上限为 200       |
| `search`    | string  | 空           | 全局搜索文本，后端负责去除首尾空白 |
| `sort`      | string  | 业务默认排序 | 逗号分隔；字段前的 `-` 表示降序    |

业务筛选使用可重复的 query 参数。例如：

```text
GET /api/v1/jobtemplate?page=2&page_size=20&search=cuda&sort=-createdAt,name&owner=mine&status=Running&status=Pending
```

要求：

- 筛选参数可以多选时，使用同名参数重复传递；
- `sort` 最多接收 3 个业务字段；
- 搜索和排序字段必须由后端白名单校验；
- 页码、页大小、搜索和筛选不合法时返回 400，不静默改写成其他含义。

### 2.2 响应结构

所有分页接口返回：

```json
{
  "code": 0,
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 10
  },
  "msg": ""
}
```

后端统一使用 `resputil.Page[T]` 和 `resputil.NewPage`。空结果的 `items` 必须是空数组，不能是 `null`。

### 2.3 查询顺序

后端必须按以下顺序处理：

```text
权限范围
-> search
-> 业务筛选
-> 排序
-> 稳定排序补充项
-> count
-> offset/limit
-> items/total/page/page_size
```

搜索、筛选或排序不能在分页之后执行，否则总数和跨页结果会错误。

### 2.4 稳定排序

每个分页查询都必须有唯一键作为最后排序项。推荐使用数据库主键 `id`，方向与业务默认排序保持一致。例如：

```text
created_at DESC, id DESC
```

如果用户指定 `sort=-createdAt,name`，实际查询仍应追加 `id`。这样相同创建时间或名称的数据不会在连续翻页时随机重复或遗漏。

## 3. 前后端职责

### 3.1 页面

业务页面只保存一份完整远程查询状态：

- 使用 `useRemoteTableState(storageKey, initialState)`；
- React Query 的 `queryKey` 必须包含规范化后的完整 `params`；
- 请求通过 `buildRemoteSearchParams` 构造；
- 搜索、筛选和页大小变化时回到第一页；
- 翻页时保留搜索、筛选和排序；
- 可使用 `keepPreviousData` 保持翻页期间的页面稳定。

### 3.2 RemoteDataTable

`RemoteDataTable` 是受控展示组件，只负责：

- 展示当前页 `items`；
- 展示后端返回的 `total`；
- 渲染搜索、筛选、排序和分页控件；
- 将用户操作传给 `RemoteTableState`；
- 空结果导致当前页越界时，回到最后一个有效页；
- 查询条件变化时清除跨页选择状态。

远程模式下不得再次执行前端搜索、筛选、排序或分页，也不得在组件内部保存第二份远程 query 状态。

### 3.3 DataTable 本地模式

现有 `DataTable` 本地模式继续保留，用于已有完整数组或外部快照。它不是远程模式的降级实现；同一个页面不能先截取一批远程数据，再交给本地模式进行第二次分页。

## 5. 有意保留的本地列表

下列页面经过审计后保留本地模式：

| 页面/组件                                  | 数据来源                | 保留原因                                                       |
| ------------------------------------------ | ----------------------- | -------------------------------------------------------------- |
| 门户总览节点、集群节点、节点标记、节点详情 | Kubernetes API/节点快照 | 一次请求用于资源汇总和节点间比较，没有数据库 `total` 语义      |
| 作业详情 Pod 表                            | Kubernetes API          | 单个作业的 Pod 快照，数量受作业规模限制                        |
| 文件系统表、数据集文件表                   | storage-server          | 目录浏览需要单独设计路径或游标协议                             |
| 审批表格本地分支                           | 已有组件兼容入口        | 现有主页面已使用远程模式，本地分支供传入完整数组的旧调用方使用 |

## 6. 兼容策略

- 不删除旧 `/jobtemplate/list`，CLI 继续使用旧接口；CLI 迁移单独安排。
- EMIAS 原有 `/aijobs` 和 `/aijobs/all` 数组接口继续保留，新页面使用 `/page`。
- 账户、用户、资源、镜像、数据集成员等旧全量接口继续服务表单候选项和现有调用方。
- 新分页接口使用独立 query key；写操作成功后同时失效分页缓存和仍在使用的旧列表缓存。
- 旧接口的删除需要先完成调用方清点、版本公告和迁移窗口，不能因页面已改完直接移除。

目前仍使用全量接口的下拉框包括用户、账户、资源、镜像和数据集未共享成员等。它们不是表格分页遗漏；数据量增长后应统一迁移到支持搜索、按需加载和已选项回显的异步选择器。

## 7. 验收清单

每个新接入页面至少验证：

1. 初次请求包含 `page/page_size`，响应包含 `items/total/page/page_size`。
2. 翻页只返回目标页数据，查询条件不丢失。
3. 修改页大小后回到第一页。
4. 搜索针对完整结果集执行，而不是只搜索当前页。
5. 筛选和排序先于分页，组合条件下 `total` 正确。
6. 相同排序值下连续翻页无重复、无遗漏。
7. 空结果显示正常；删除最后一页数据后能回到有效页。
8. 非法页码、页大小、筛选值和排序字段返回 400。
9. 写操作后当前分页查询和相关 facets 能刷新。
10. 旧接口和依赖旧接口的 CLI/表单仍可使用。

前端公共远程状态协议测试可通过以下命令运行：

```shell
cd frontend
pnpm test:data-list
pnpm exec tsc --noEmit
pnpm build
```

后端业务包至少应完成编译和对应查询测试。部分 handler 包在测试启动时会加载开发配置和数据库；环境不可用时，应明确记录“包编译通过、数据库集成测试未执行”，不能把编译结果描述成真实数据验收通过。

## 8. 新列表接入步骤

1. 判断数据源和增长方式，确认它属于数据库主列表。
2. 定义权限范围、搜索字段、业务筛选和排序白名单。
3. 后端实现统一请求/响应协议，并追加唯一键稳定排序。
4. 保留仍有调用方的旧接口。
5. 页面使用 `useRemoteTableState` 和 React Query 持有唯一远程状态。
6. 使用 `RemoteDataTable` 展示，不进行第二次本地处理。
7. 增加参数校验、稳定排序、空结果和页码越界测试。
8. 用浏览器 Network 面板核对真实请求和响应，再提交独立 commit。
